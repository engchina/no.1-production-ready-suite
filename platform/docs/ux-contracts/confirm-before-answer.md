# 回答前の確認（Confirm before answer。#1839）

利用者の質問が曖昧なとき、回答（NL2SQL は SQL の生成）の前にシステムから確かめる仕組みの、3 製品共通の振る舞いの正本。部品は `@production-ready/ui` の `ClarificationCard`（確認のカード）と `ClarificationRecord`（会話に残す表示）で、見た目と props は [design-system README §4「`ClarificationCard` / `ClarificationRecord`」](../design-system/README.md) と [components-reference.md](../design-system/components-reference.md#clarificationcard--clarificationrecord--新規1839) にある。

> 段 1（#1839）は部品とこの契約だけ。製品の画面は段 2（NL2SQL）・段 3（RAG）・段 4（Agent）で載せ替える。載せ替えるまでの今の実装は NL2SQL `features/nl2sql/components/RequirementClarification.tsx`、RAG `components/chat/ClarificationChoice.tsx`。

## 1. 用語

利用者の入力は「質問」（AGENTS.md「言語」）なので、システムから利用者に聞くものを「質問」と呼ばない。3 製品で同じ書き方にし、製品の名詞（〈回答〉/〈SQL の生成〉）だけを変える。文言の正本は `clarificationLabels({ stage, action })`（`packages/ui/src/components/chat/clarification-labels.ts`）。

| 場所 | 用語 |
|---|---|
| 機能の総称（設定・文書・説明） | **回答前の確認** |
| カードの題 | 「〈回答 / SQL の生成〉の前に確認させてください」 |
| 1 件の確認 | **確認事項** |
| 聞く理由 | **確認する理由** |
| 選択肢・自由入力 | 選択肢 /「その他（自由入力）」（常に出す） |
| 確定 | 「この内容で〈回答 / SQL を生成〉」 |
| スキップ | 「確認せずに〈回答 / SQL を生成〉」＋補足「前提を示して〈回答 / SQL を生成〉します。」 |
| キャンセル | 「確認をやめる」＋補足「質問は入力欄に戻ります。」 |
| 会話に残す表示 | **回答前に確認した内容**（NL2SQL は「SQL の生成前に確認した内容」） |
| 業務の単位の設定 | 節「回答前の確認」、方針「曖昧な質問の扱い: 確認してから回答する / 前提を示して回答する」、「確認の上限（往復）」 |
| Agent のツール | `ask_user_confirmation` |

- NL2SQL の「AI要件確認」はこの総称にそろえ、画面の名前も「回答前の確認」にした（#1839 の段 2。NL2SQL の i18n の `CONFIRM_FEATURE`）。

## 2. いつ聞くか

業界の基準（Amazon Alexa の研究、NAACL 2025 IntentSim、Adobe の企業向け assistant の研究、PAQA）に合わせ、**必要なときだけ聞く**。すべての質問で聞き返すと体験が悪くなる。

| 聞く | 聞かない（前提を示して答える） |
|---|---|
| 解釈が割れ（2 つ以上の読み方が同じくらいあり得る）、**誤りの代償が大きい**とき（集計の対象・期間・指標の取り違え、手続きの対象の取り違え） | 明らかな質問（読み方が 1 つ。質問の言葉・会話の前の往復・業務の単位の既定で決まる） |
| 検索の結果が**別の対象・版**に割れたとき（RAG で、製品・版・地域ごとに答えが違う資料が当たった） | 割れていても答えが変わらないとき |
| 答えるのに要る条件（業務ガイドの条件・SQL の SELECT / FROM など最低の基準）が質問から決まらないとき | 範囲外・確かめられない質問（拒答する。#1835） |

- 曖昧 → 確認、範囲外・確かめられない → 拒答（#1835）。拒答の代わりに確認を使わない。
- 聞くかどうかの判定は backend（モデル・ルール）が行い、画面は判定の結果（確認事項の有無）だけを見る。

## 3. 出し方

- 確認のカードは、**利用者の質問の直後の回答の場所**（`ChatAnswer` の中。回答の枠の中なら `variant="plain"`）に出す。別の画面・ダイアログにしない（会話の流れを保つ）。SQL 生成の画面など会話でない画面は、結果を出す場所のパネルに出す（`size="lg"`）。
- 1 枚のカードの中身は、上から 題（と位置・往復）→ 確認事項（確認事項の文・確認する理由・選択肢・「その他（自由入力）」）→ 製品の中身（任意）→ 失敗 → 操作の行 → 補足（押せない理由・スキップとキャンセルの説明）。
- **確認事項は 1 回 1 件を既定にする**（Google の conversation design。一度に多くを聞かない）。続けて聞くときは 1 件ずつ出し、題の上に「確認事項 1 / 3」を出す（`progress`）。まとめて聞く方が早い（互いに独立した 2〜3 件）ときだけ 1 枚に並べ、「確認事項 2 件」を出す。
- **選択肢は 1 回 8 個まで**、名前は 1 行で読める短い文にし、補足は説明（`description`）に分ける。製品固有の中身（NL2SQL の物理名・根拠、RAG の章節）は選択肢の `detail` に置く。
- 1 つだけ選ぶ確認事項はラジオ、複数選べる確認事項はチェックボックス（「当てはまるものをすべて選べます。」）。
- **「その他（自由入力）」は常に出す**（選択肢に無い答えの逃げ道。Copilot Studio・ECLAIR・Google Chat の確認のカード）。1 つだけ選ぶ確認事項では選択肢と自由入力はどちらか一方（選ぶと自由入力を空に、書くと選択を外す）、複数選べる確認事項では併せて答えられる。自由入力を値に当てはめられないときの扱いは製品が決め、黙って捨てない（モデルに文として渡すか、当てはめられないことを示す）。

## 4. 操作と結果

| 操作 | 結果 |
|---|---|
| 「この内容で〈回答〉」（primary） | 答えを構造化して backend へ送り（確認事項の ID・選んだ選択肢の ID・自由入力）、回答に進む。すべての確認事項に答えるまで押せない |
| 「確認せずに〈回答〉」（secondary） | 確かめずに、**前提を示して**回答する（回答の中で何を前提にしたかを書く）。答える前でも押せる |
| 「確認をやめる」（ghost、操作の行の右端） | 確認と回答をやめ、**質問を入力欄に戻す**（書き直して送れる）。会話には何も残さない。答える前でも押せる |

- 押せない理由（「選択肢を選ぶか、「その他（自由入力）」に書くと押せます。」、複数なら残りの件数）は操作の行の下に出し、確定のボタンの `aria-describedby` で結ぶ（#1772 / #1776）。製品固有の理由（NL2SQL の未送信の直し）は `blockedReason` で渡す。
- 処理中は押したボタンだけを `loading` にし、ほかの操作・選択肢・自由入力を押せなくする（[buttons.md §8](./buttons.md#8-アイコン--ローディング)）。選んだ内容は処理中も見える。
- 送信の失敗は操作の行の直上に danger の `ApiErrorBanner`（`error`）で出し、入力した答えは残す（[messaging.md §10](./messaging.md#10-操作の結果状態の出し方位置幅形出す情報705)）。
- 確定・スキップの後はカードを閉じ、§6 の表示に置き換える。

## 5. 往復の上限

- 確認の往復（確認 → 答え → まだ曖昧なら再び確認）には上限を置く。**既定は 2 回**（Copilot Studio は 2 回で引き継ぐ）。業務の単位の設定で変えられる（§8）。
- カードの題の上に「確認 1 回目（上限 2 回）」を出す（`round`）。上限の回では「これが最後の確認です。決まらない点は前提を示して〈回答〉します。」を添える。
- 上限に達したら、それ以上は聞かずに前提を示して回答する（スキップと同じ扱い）。

## 6. 履歴（会話に残す表示）

- 利用者の答えは**利用者の発言として会話に残す**（`ClarificationRecord` の `variant="bubble"`。右寄せの吹き出しで「回答前に確認した内容」と、確認事項ごとの答え）。スキップは「確認せずに回答しました（前提を示して回答）」を残す。キャンセルは残さない（質問が入力欄に戻るため）。
- 回答の詳細でも確かめられるよう、回答の枠の中の折りたたみ（`variant="disclosure"`）に同じ内容を出してよい（NL2SQL の旧「AI要件確認で確かめた質問」の置き換え）。並びは回答の根拠の側（[page-archetypes.md §6.1](./page-archetypes.md#61-骨格) の「根拠を先、実行記録を後」）。
- 会話を開き直したときも同じ表示にする（答えは backend の会話の記録に残し、画面の状態だけに持たない）。

## 7. 状態の保持とアクセシビリティ

- 答えていない確認は**作業状態**（[workspace-state.md](./workspace-state.md)）。同じ会話に戻ったら、開いている確認のカードを backend の状態から出し直す。入力中の答えは下書きとして残してよい（`value` / `onValueChange` で受控にし、同じタブの一時保存）。対象（プロファイル・業務 Agent）を変えたら開いている確認を外す。
- ページに戻っただけで確認を送り直さない。古い確認（会話が先へ進んだ）は `disabled` にするか出さない。
- カードは `<section>` で、題（見出し。既定 h3）を名前にする。確認事項は `fieldset` で、確認事項の文（題の 1 段下の見出し）を名前、確認する理由と複数選択の補足を説明にする。選択肢はネイティブのラジオ・チェックボックス（矢印キーで移る）。
- 確認事項が変わったら（1 件ずつ聞く・往復の 2 回目）最初の確認事項の文へフォーカスを移し、読み上げで新しい確認事項をそのまま聞けるようにする。最初に出たときは既定でフォーカスを動かさない（入力欄で書いている利用者の位置を奪わない。会話の欄の `role="log"` が読み上げる）。
- 選択肢の行は 44px 以上（`--control-height-touch`）。375px では操作の行を縦に並べ（主操作を上）、各ボタンを全幅にする。状態は色だけで示さない（選んだ選択肢はラジオ・チェックの印でも示す）。

## 8. 3 製品の割り当てと業務の単位の設定

| 製品 | いつ出すか | 確認事項を作るもの | 業務の単位の設定の場所 |
|---|---|---|---|
| NL2SQL | 送信の後、**SQL の生成の前**（旧名「AI要件確認」） | オントロジーと要件の検査（`ClarificationMode`） | **業務プロファイル**（回答前の確認の方針・上限） |
| RAG | 送信の後、**回答の前**（検索・回答プロファイルのルールの確認、業務ガイドの条件の確認、検索の結果が別の対象・版に割れたとき） | プロファイルのルールごとの確認（#717）・業務ガイドの条件（#1238） | **検索・回答プロファイル**（ルールごとの確認＋プロファイルの方針） |
| Agent | **ツールの結果**（NL2SQL・RAG の確認を受け渡す）か、**Agent 自身の確認**（`ask_user_confirmation`） | 呼んだ製品（受け渡すだけ。二重に定義しない）/ Agent のモデル | **業務 Agent**（方針・上限） |

- 方針の既定は「確認してから回答する」、上限は 2 回。「前提を示して回答する」を選んだ業務の単位では、確認のカードを出さずに前提を示して回答する。
- 製品の文書（`docs/frontend-*.md`）には、この契約が決めない製品固有の差分（確認事項の作り方・自由入力の当てはめ方）だけを書く。
