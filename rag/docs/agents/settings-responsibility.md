# RAG の設定責務（3 層モデル）

> rag/AGENTS.md から移した詳細（#2276）。rag/AGENTS.md の規則と同じ強さで守る。規則を変えるときはこのファイルを直し、AGENTS.md には規則の要約と案内だけを書く。

## RAG 設定責務

> **3 層モデル（確定）**: 文書 = 処理レシピを持つ / KB = 純スコープ（コレクション）/ Search Answer Profile → KB。
> KB は「レシピ」と「検索スコープ」を兼任しない。レシピは文書単位、検索・回答設定は Search Answer Profile。

### 文書（Document）= レシピ

文書は中身に加えて **1〜3 件の独立した処理レシピ（preprocess / parser / chunking）** を自身のプロパティとして持つ。各レシピは設定、ジョブ、成果物、エラー、工程状態を個別に保持する。

- ファイル準備（preprocess）。旧形式・マクロ付き・テンプレートの Office（.doc / .ppt / .xls・.docm / .pptm / .xlsm・.dotx / .dotm / .potx / .potm / .xltx / .xltm。#4054）と ODT・RTF（.odt / .rtf。#3351）は原本のままでは解析せず、文書レシピで変換を選んだときだけ取り込む（Word・PowerPoint・ODT・RTF は Office→PDF（Word は Word→JSONL も可）、Excel は Excel→JSONL。Office→PDF は Excel を変換しない。マクロは実行しない。判定は `backend/app/rag/parser_source_guard.py`。テンプレートは拡張子・MIME type と原本の package の種類を保存の前に照らす〔`backend/app/rag/office_template.py`〕。#2470）。
- 文書解析（parser / OCR engine）と、図・画像の読み取り（Vision。解析エンジンに関係なく解析の後に backend の共通の段で読み取る。切り替えはレシピだけ）。global の既定エンジンは Docling（PDF と画像だけ）。それ以外の形式は取込前に止めて処理レシピで Unstructured などを選ぶよう案内し、自動では振り分けない（判定は `backend/app/rag/parser_source_guard.py` の 1 か所。Unstructured のサービスは統合 stack の既定で配備する。#1559）。XML ツリー JSON（tag / attr / children の木の JSON。parser-xml-tree-json）も Docling・Unstructured と同じ使用エンジンの 1 つで、選んだときだけ使う（形式で自動には振り分けない。対応しない形の JSON は取込で扱えない旨のエラーにする。サービスは既定で配備し、既定は停止（使うときはサービス管理画面で起動する）。#2042・#2453）。構造化レコード JSONL（前処理 csv_to_jsonl / excel_to_jsonl / word_to_jsonl の成果物。parser-structured-records-jsonl）も同じく選んだときだけ使う使用エンジンで、文書レシピの分割方式「固定分割」と組み合わせると記録の境界で 1 記録 1 chunk になる（解析と分割はどちらも文書レシピの層。#2457）。Docling / Unstructured はこの JSONL を受けず、取込の前に「構造化レコード JSONL を選ぶ」診断で止める（黙って変換しない）。画面でファイル準備に CSV→JSONL・Excel→JSONL・Word→JSONL を選ぶと、解析エンジンと分割（固定分割符・既定の分割符 `<<<JSONL_RECORD_BOUNDARY>>>`）を見える上書きとして入れて保存する（実行時に隠れて切り替えない）。
- 文書分割（chunking strategy、chunk size、overlap、parent-child）。
- 索引構築（vector index build、GraphRAG、navigation summary、field extraction）。
- 品質 gate（解析品質、chunk 品質、公開前チェック）。

レシピの既定値は **global（「取込・検索・回答設定」配下の ファイル準備 / 文書解析 / 文書分割 など）** から解決し、各レシピが選んだ値で上書きする。**KB からは解決しない**。

**形式別の既定（`/settings/file-type-defaults`。#4732）** は全体の設定の 1 つで、PDF・Word・PowerPoint・Excel・CSV・テキスト（.txt）・Markdown・JSON・HTML・画像の形式ごとに、ファイル準備・解析エンジン・分割方式を選ぶ（分割のサイズなどのパラメータは全体の既定に従う。構造化レコードの行の固定分割符だけは記録の境界にする）。解決の順は **文書のレシピ > 形式別の既定 > 全体の既定**。保存値の無い行には組み込みの既定（`BUILTIN_FILE_TYPE_DEFAULTS`）を使い、「全体の既定に従う」を保存した行は全体の既定に従う。組み込みの行が要るファイル準備・解析エンジンが無効な環境では、その行は全体の既定に従い、画面に理由を出す。「既定に戻す」は組み込みの値を画面に入れるだけで、「保存」で確定する。アップロードのときにレシピへ写さず、実行時に解決する（レシピの明示値は変えない）。種類は拡張子と content type の形式の解析だけで決め（`backend/app/rag/file_type_defaults.py` の 1 か所）、受け付ける形式に無いものは全体の既定に従う。保存時に行ごとの組み合わせを検証する（422 と何を直すかの文言）。保存は取り込み済みの文書を変えず、実効値がずれた文書はレシピの再処理の案内（`needs_reprocessing`）で分かる。KB・Search Answer Profile の層には関わらない。embedding / HNSW は単一固定。同じ文書のジョブは直列実行し、異なる文書のジョブは並行実行できる。

### ナレッジベース（KB）= コレクション（純スコープ）

KB は **どの文書を検索対象にするか（membership）だけ**を持つ純スコープ。**レシピ（preprocess / parser / chunking）も検索・回答設定も持たない**。

- 文書 membership（N:N。1 文書が複数 KB に所属可、1 KB が複数文書を束ねる）。
- 名称 / 説明 / スコープ。
- 文書構造索引の構築だけは、KBごとの未指定/ON/OFFでレシピ・全体設定を上書きできる。未指定は従来のレシピ/全体設定に従う。解析・分割・embedding・検索拡張は上書きしない。保存だけでは既存成果を変更せず、KB詳細の補建操作で現在有効なChunkの構造情報から構築する。構築の進捗と版をOracleに保存し、他KBの図は変更しない。OFFでも既存図を削除しない。
- 例外として、項目抽出の項目の定義（何を取り出すか）は KB ごとに持てる（無ければ全体の既定、複数 KB に属する文書は和集合。docs/knowledge-base-management.md の 8.4.1a）。項目抽出を行うかどうかは文書レシピ / global が決める。

文書の KB 出し入れは `rag_document_knowledge_bases` の行 add/delete **のみ**で、chunk へ波及しない（再プラン / materialize / GC を起こさない）。KB UI から preprocess / parser / chunking・検索方法・安全チェック・品質評価を出さない。KB の legacy adapter/query config は読み取りのみ許容し、runtime では使わず、次回保存で再保存しない。

実体・別名索引は全体の専用設定画面（`/settings/entity-index`）で構築の既定を選び、文書レシピで上書きする。既定は OFF。文脈ヘッダは RAG_CHUNK_CONTEXT_HEADER_ENABLED（既定 true）で全体に適用し、画面や文書レシピでは切り替えない。旧レシピの明示値は読み捨てる。変更を既存の文書へ反映するには該当工程から再処理する。検索インデックスへの導線は共有の全体設定だけを開き、文書レシピの上書きにはしない。

### Search Answer Profile

Search Answer Profile は **検索・回答に使う設定だけ**を持つ。

- 参照 KB scope。
- 検索方法（回答の検索と生成）、安全チェック。
- feedback 集計。

設定責務は次の通りとし、検索・回答プロファイルには Sidebar 全項目を複製しない。

| 設定群 | グローバル既定 | 文書レシピ上書き | Search Answer Profile 上書き |
|---|---|---|---|
| ファイル準備 / 文書解析 / 文書分割 / GraphRAG | 可 | 可 | 不可 |
| 検索インデックス | 可 | 不可 | 不可 |
| 検索方法 / 安全チェック | 可 | 不可 | 一部（検索方法の質問の言い換え・分解・回答の生成方式・rerank・各種の拡張などは全体設定だけ。プロファイルの `query` が持つ欄は `app/rag/kb_adapter_config.py` の `KnowledgeBaseQueryConfig` が正本。#4784） |
| 回答プロンプト | 可 | 不可 | 不可 |
| 品質評価 | 可 | 不可 | 不可 |

文書構造索引の構築（構築する / しない。文書と章・節の見出しのつながり）は文書レシピの指定をKB別の構築指定で上書きできる（ナレッジベースの文書構造グラフで見られる。回答の検索で使うか〔当たった根拠と同じ狭い章節・表の根拠と、質問に見出しの語が含まれる章節の根拠を候補に足す。既定 OFF〕は検索方法の全体設定の「文書構造による検索拡張」〔`graph_expansion_enabled`。#2055。件数の上限 `graph_expansion_max_chunks` も含め、検索・回答プロファイルでは上書きしない〕で選ぶ。LLM で意味の entity を抜き出す取込と claims / community summary の構築は持たない）。共有 Oracle 索引の設定は Search Answer Profile へ保存しない。

検索時の解決順は **request 明示 > Published Search Answer Profile > global defaults**。KB は `query` の値を持たない（#4784）。

### 複数レシピ融合（精度向上）

同じ文書の検索精度を上げたい場合はレシピを最大 3 件まで追加し、それぞれを独立して materialize する。**各レシピの直近成功した active chunk_set はすべて検索対象**とし、hybrid RRF + rerank で融合する。回答に渡す根拠の選択（`rag_engine` の `evidence_spans`）では、本文が同じ根拠に加えて、同じ文書で解析の要素の ID（`element_ids`。親子分割の親は子の `source_record_refs`）が小さい側の 8 割以上重なり、短い側の本文の 9 割以上がもう一方に含まれる根拠を 1 つにまとめる（source-span 重複除去。順位の高い位置に範囲の広いほうを残し、まとめた chunk_id は `source_aliases` に残す。要素の ID の無い分割は本文が同じものだけをまとめる。#1331）。主レシピ、候補、配信中、昇格の概念は持たず、配信モード（`single / fused / routed`）の設定も持たない。設定変更後の再処理中や再処理失敗時も、直前の active chunk_set を検索対象として維持する。KB membership を変えてもレシピ集合や chunk_set は変わらない。

レシピ追加・削除は親文書行をロックして **最少 1 件・最大 3 件**を保証する。活動中ジョブのあるレシピは編集・削除できない。成功時だけ新 chunk_set を active に原子切替し、失敗時は他レシピと旧 active 出力を変更しない。文書単位の再取込も同じで、検索に出している版は切替まで残し、処理の進み具合はレシピの status で示す（文書の status は `INDEXED` のまま。#4115）。

版に属するデータは chunk_set から辿る（#4166）。章節の対応は chunk_set ごとに置き換え、ほかの版の行を消さない（chunk_set の行を消す処理が一緒に消す）。解析したファイルは抽出の `parser_artifacts.source_derivation` が正本で、根拠の読み取りはレシピの行の `preprocess_artifact`（最後のファイル準備の結果。確認の画面が見る）ではなくここを読む。記録の無い版は別のファイルで代用せず、ファイルが無いエラーにする。

切替は「job の開始時の active が今も active で、その実行が今も job を持っている」ときだけ行う（`activate_recipe_chunk_set` の transaction の中で確かめる。#4167）。active が変わっていたら候補を捨て、job は失敗ではなく `SKIPPED`（`skip_reason` = `superseded_by_newer_version`）にする。再解析は高価なので自動でやり直さない。切替のたびに `rag_recipe_version_log` へ 1 行を足す（親の版・原本の hash・抽出の ID・分割までの入力の ID・言語資源の公開版・chunk の数・job）。この表は chunk_set に FK を持たず、旧版の行を消しても残り、文書・レシピの削除で消える。本文・質問は入れない。

切替（commit）と旧版の削除（expire）は分ける（#4168）。切替は旧版に `retired_at` を付けるだけで行を消さない（一度も active にならなかった候補だけは切替で消す）。検索・回答・件数・回答の監査は今までどおり active だけを見る。根拠を ID で読む経路（`readable_version_chunk`・`rag_read_source`・`rag_read_section` の版の指定と cursor・定位子・引用のプレビュー）だけが退役した版を読む。権限・テナントの条件は同じ。旧版の抽出も上書きしない（`served_extraction_ids`）。清掃（`chunk_set_retention`）はレシピの行を lock して、退役の新しい順に `RAG_CHUNK_SET_RETAINED_VERSIONS` を超えた版と `RAG_CHUNK_SET_RETENTION_DAYS` を超えた版を `_delete_chunk_set_outputs` で消し、どこからも参照されなくなった `artifacts/canonical/…` のファイルを文書の削除と同じ後始末の記録で消す。同じレシピに QUEUED / RUNNING の取込 job があれば待つ。何度実行しても同じ結果になる。清掃の後の根拠は `source_stale` の案内になる。既定は直前の 1 版を 7 日。

抽出の確認の修正は文書レシピの層で版にする（#2644。`rag_document_extraction_revisions`）。保存と復元のたびに新しい ID の抽出と不変の版を作り、親の版と基にした解析の版を記録する。過去の版の行は書き換えない。解析の結果は最初の保存のときに版にする（修正しない文書に写しを持たない）。解析をやり直した後は修正の前提が変わったことを画面で示し、自動で取り込まない。原本か解析の設定が今と違う版は復元しない。復元は確認待ちのレシピだけで、検索に出している版は次の切替まで変わらない。版の数の上限は `RAG_EXTRACTION_MAX_REVISIONS`（今の版・基の解析の版・検索に出している版は残す）。

人が修正した章節は文書の層で版にする（#4171。`rag_document_section_revisions`）。章節はすべての処理レシピで共有する文書の属性なので、抽出の版と別の表に置く。保存・復元・抽出結果への戻しのたびに不変の版を足し、`rag_document_sections` は今の修正の 1 行のまま持つ（`revision` は今の版の番号）。各版に基にした抽出の ID と抽出の章節の指紋を記録し、今の抽出と違えば画面で示す（ID だけでは同じ設定の再解析と章節の抽出規則の変更を見分けられず、文の修正を章節の変更と見誤るので、指紋も比べる）。保存した修正は自動で書き換えない（人が変えていない章節のページの追従と新しい章節の追加は、今までどおり読むときに行う）。章節を変えても chunk は変えず、章節と chunk の対応だけを作り直す。版の数の上限は `RAG_SECTION_MAX_REVISIONS`（今の版は残す）。

GraphRAG、navigation summary、field extraction が planning のみで実 materialize 未完の場合は、UI / API diagnostics にその状態を表示する。

### 章節の抽出規則と章節の要約

文書解析の「解析後の処理」は、図・画像の読み取り → 見出しの階層の推定 → メタデータ/項目抽出 → 章節の抽出規則 → 章節の要約の順に並べる。規則は要約スイッチの内側に置かず、独立して編集・保存する。

「章節の抽出規則」は章節ナビゲーションの章節を保存済みの抽出結果から作る独立した設定で、要約が無効でも適用する。LLM や再取込は不要。「章節の要約」は取込時の章節の抽出規則で作る各章節へ要約を付け、検索可能な要素にもする処理を選ぶ。要約を無効にしても章節の木は作る。

規則の方式を変えて保存済み要約と現在の章節が対応しない場合は、章節ナビゲーションに未対応の件数と確認方法を表示する（#3011）。名前・ページの類似で別の章節に要約を付け替えない。現在の規則で要約するには抽出から再処理する。解析見出しの木は別に保ち、再取込なしの方式切替と MCP の章節の契約を維持する。

### 機能別のプロンプト設定

文書解析の設定に Dots.OCR・図と画像の読み取り・見出し階層の推定・項目抽出・章節の要約の編集欄を置く。各欄は共通の Disclosure と編集操作（保存・変更を破棄・既定に戻す）を使う。検索方法の画面には質問の解釈・検索・根拠の判定の編集可能なプロンプトを処理順に示す。条件認識（`support_guide_conditions`）だけは question 区分の例外として回答プロンプトに置き、他の質問解釈の段は検索方法に残す。条件認識も保存した指示を要求単位で実行に反映する。品質評価の段は評価の基準に示し、検索・取込の段とともに重複表示しない。

全体のプロンプトは `rag_answer_prompts` にキーごとに保存し、文書レシピでは上書きしない。変更は次の該当する段から使う。既存の成果物を変えるには再処理する。未編集・読込失敗はコードの既定値を使う。各キーの変更には配置先の設定画面の権限を求める。

実行の順は、文書解析 → 図・画像 → 見出し階層 → 項目抽出 → 章節の要約 → 文書分割 → Embedding・索引。章節の要約は章節の本文から作る。

派生の項目・章節要約は分割方式に関係なく独立した検索 Chunk にする。本文の親グループへは混ぜない。要約の元の要素 ID、項目の元の要素 ID と派生の印を保存し、検索で当たった後は同じ Chunk 集合の原文だけを回答の根拠にする。検索用の Chunk を追加する生成機能は、Chunk 集合のキーにも含める（#3016）。

### 回答の品質評価

「回答の品質評価」は標準回答・必須要点と照らす品質評価の指示として、評価の基準に置く。双方は共通の編集欄を使い、それぞれの配置先の設定権限で保存・既定への復帰を許可する。構造化出力の型とアクセス制御はコードが保証し、編集の対象にしない。

原文照合済みの出典を「見出しだけの引用」として外す判定には、道筋に対応する明示的な見出しの出所（`section_path_sources`）を必要とする。出所未記録の `section_path`、柱・本文の昇格・画面経路の推定は、本文ではないことの確定根拠にしない。引用の存在と主張の裏付けは区別し、原文照合・主張の検査・評価の閾値は維持する。

### 業務ガイドの使用

業務ガイドを質問への回答に使うかは検索・回答プロファイルの `query.support_guide_enabled` で選ぶ。画面の操作は「業務ガイドを使用する」の単一スイッチ。未指定・null は OFF とし、既存プロファイルを自動的に ON へ移行しない。手順ごとの検索の ON / OFF と回数・時間上限は全体設定だけで決め、検索・回答プロファイルでは上書きしない（#3523）。全体の実行設定 `RAG_SUPPORT_GUIDE_ENABLED` も既定 OFF。プロファイルでは明示的に ON にした場合だけ使う。

OFF は検索・チャット送信前の確認・MCP の `rag_lookup_guides` で同じく適用し、ガイドの読み込み・選択・条件の確認・回答への適用・手順別検索を行わない。通常の検索と用語・同義語・回答ルールは継続する。意味の照合と近い候補の確認は全体設定（`RAG_SUPPORT_GUIDE_SEMANTIC_MATCH_*`・`RAG_SUPPORT_GUIDE_CLOSE_MATCH_*`）だけで決め、検索・回答プロファイルでは持たない（#4784）。総合 ON のときだけ従う。公開・編集は引き続き可能。管理画面で明示的に実行する下書き試答は、その回答だけガイドを有効にする。プロファイルの保存値と通常の回答は変更しない。

検索方法の質問拡張・回答フロー・前後の chunk 数・rerank・項目条件・実体・別名による検索拡張と件数・文書構造による検索拡張と件数・画面目録・章節の拡張と段数と入力割合・業務ガイドの手順ごとの検索と回数・時間の上限は全体設定で管理する。検索・回答プロファイルの `query` はこれらの欄を持たず、API に送ると検証エラーになる（#4784）。表示順は初回の呼出順（項目条件 → 名称別名 → 関係情報 → 画面目録 → rerank → 章節）に合わせる。追加検索でも同じ拡張・rerank・章節補完を再利用するため、一度しか実行しない意味ではない。

検索文・検索経路ごとの取得件数は全体設定の `rag_retrieval_query_limit` で管理する。再ランキング後の採用件数は独立した全体設定 `rag_rerank_top_n` で、0 は追加制限なし。採点と関連度の下限による選別が成功した後だけ適用し、引用元と参照先の組を分けずに上限内で選ぶ。明示添付とその参照先は既存の別枠で保持する。回答起点数 `top_k` を満たすために普通候補を補い直さない。親章節・隣接原文の補足や、送信する総 Chunk 数の上限ではない。再ランキングの未実行・失敗時はこの採用上限を使わず既存の取得順を維持する。


章節の抽出規則は「解析済みの見出し」「番号の規則」「独自の規則」として対象を明示する。既存5方式の識別子は維持し、法令型・公用文型・小数番号型は対応する番号構造が異なるため別のプリセットとして残す。保存前の候補確認は、利用者が見られる文書と既存レシピの保存済み抽出だけを読み、指定した未保存の方式・規則を適用する。レシピ作成・設定保存・取込・モデル呼出は行わない。人が編集した最終章節とは区別し、レシピによる方式の上書きがあるときは明示する。

## 回答前の確認と前提の明示

`SearchAnswerProfile.clarification_policy` は検索・回答プロファイルの責務とする。`confirm` は質問に一致した未回答の確認事項を提示し、`assume` は確認カードを出さず、一致した未回答のルール・業務ガイドの条件を回答生成へ渡す。回答生成の system 指示で未確定の条件・仮定と資料の事実を区別する。未回答の選択肢を検索の条件や利用者の事実として補わない。利用者が明示した条件・選択済みの答えは引き続き適用する。検索・チャット・MCP は共通の回答入口で解決し、公開されたプロファイルやルールの保存値は変えない。

名称・別名の拡張、画面目録は全体設定の既定を OFF とし、明示的に有効化した場合だけ使う。保存済みの明示値は変更しない。

検索・回答・評価の指示は `PROMPT_STAGES` の段と部分に対応する key で保存する。保存値・既定値・画面に出す内容・実行の参照を同じ一覧に結び付け、要求ごとに固定し並行要求へ漏らさない。評価器の版と標準回答の範囲の cache には有効な指示を含める。既定への復帰は編集欄の内容を戻すだけで、保存時に上書きを削除する。保存前なら変更を破棄できる。
