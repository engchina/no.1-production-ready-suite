## 読み取れること

- 時間の大半はモデル（LLM）の呼び出し。1 問で 3〜5 回呼び、1 回は 8〜20 秒かかる。検索（Oracle AI Vector Search と
  Oracle Text の hybrid）は 4 秒前後、Rerank は 0.1 秒で、全体の 1 割に満たない。
- 回答の監査で不合格になると修復の round（2 回目の生成と根拠確認）が走り、15〜22 秒が足される。
- クライアントから見た時間はサーバーの `elapsed_ms` より 16 秒前後長い。`elapsed_ms` に入らない前後の処理
  （検索・回答プロファイルの読み込み・安全チェック・記録の保存など）の時間と考えるが、内訳は未確認。

## #1218 の判断（2026-10-07）

計測の結果、今の待ち時間（1 問 50〜80 秒）の大半はモデルの呼び出しの回数と 1 回の時間で決まる。引き継ぎの提案のうち、
モデルの呼び出しを増やす仕組みは、精度の向上を評価で示せるまで入れない。

| 項目 | 判断 | 理由 |
|---|---|---|
| 根拠の MCP（evidence・`rag_read_source`） | 実施済み（#1219） | 呼び出しを増やさずに根拠の場所・版を渡せる |
| Excel の前処理（表頭・行とセルの場所・手順書） | 実施済み（#1221 / #1224） | 取込の質の改善で、回答の時間を増やさない |
| 評価の分類と内訳・工程ごとの計測 | 実施済み（#1226） | 以降の判断の材料 |
| 軽量の業務ガイド（適用条件・必要な証拠・引き継ぎの条件） | 今は入れない | 顧客の業務の内容（リポジトリの外）が要り、効果を示す評価のデータがまだ無い。分類付きの評価セットで「条件の確認が要る」質問の失敗が多いと分かったら再検討する |
| 覆域の行列と欠けた所だけの再検索 | 今は入れない | 再検索と判定でモデルの呼び出しが増える。修復の round（上の 2 回目）がすでにあり、その回数・効果を先に評価で見る |
| 回答の構造化と共通の最終検証（Agent の出力も） | 今は入れない | 監査（根拠確認）はすでに回答フローの中にある。Agent の出力に別の LLM の検証を足すと 1 問 20 秒前後増える |
| Agent の支援タスクの状態（Run をまたぐ確認） | 今は入れない | 「現場のデータが要る」「条件の確認が要る」分類の評価で必要性を示してから |

次に効く改善の候補は、モデルの呼び出しの回数（修復の round が走る条件）と、`elapsed_ms` の外の 16 秒の内訳の調査。
