# 業務支援の改修の実装の対応表（#1218 / #1254）

業務支援の RAG と Agent の改修（引き継ぎ文書 `../rag_poc/handoff.md`。以下 handoff）を、どの Issue / PR で
実装したか、どこを推奨案に変えたか、何を見送ったかを handoff の節ごとに記録する。計測の値と、計測にもとづく
最初の判断は [answer-baseline-2026-10.md](./answer-baseline-2026-10.md) にある。

状態の凡例: **済** = main に merge 済み / **確認待ち** = draft PR（設計・既定値を人が確認してから merge）/
**見送り** = 今は実装しない（理由を書く）。

## 進め方

- 計測を先に行い（#1226）、合成の評価セット（#1231）で効果と課題を確かめながら進めた。
- モデルの呼び出しを増やす仕組み・データモデル・回答の挙動を変える仕組みは、推奨案で実装して draft PR に
  し、人の確認を待つ。既定は回答時間を増やさない側にした。
- 顧客の資料・質問は使わない。評価・例はすべて架空の「サンプル業務ポータル」。

## 計測と評価で分かったこと（2026-10-07）

- 回答の時間の大半はモデルの呼び出し（1 問 3〜5 回、50〜110 秒）。確認が要るときに回答を作らずに確認を返すと
  5 秒で返せた（#1238 の実環境の確認）。
- 合成の評価セット（#1231）の結果: 対応の正しさ 0.80。確認が要る質問に確かめない・古い版を混ぜる・関係の
  薄い原文で拒答しない、が主な課題で、それぞれ #1238・#1248・（未対応）に当たる。
- 業務ガイドで条件を渡しても、モデルが既知の条件で手順を絞らないことがある（#1240 の既知の制約）。

## 比較の後に直したこと（2026-10-08）

- 確認の質問・人への引き継ぎを、評価で拒答・検索の取りこぼしと数えない（#1259。済）。
- 関係の薄い原文を示して拒答しない問題（#1256。済）。
- 業務ガイドの条件の言い換え（#1237 / #1238。確認待ち）。
- 既知の条件に当たる場合の手順だけを答えるよう回答の材料で指示する（#1238。確認待ち。手順の文が両方の場合を
  書いた 1 段落のときは、言い換えで両方が残ることがある）。
