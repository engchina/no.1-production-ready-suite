# 視覚補足の回答本文と検索本文（#2728、Draftで検証中）

検索用に生成した補助語は画像中の逐語原文ではない。文書レシピの視覚補足から、回答に渡す本文と検索に使う本文を分ける。KBの所属条件・権限には除外規則を追加しない。

## 共通の内部契約

- `VisionTextProjection` は版、`answer_description`、`index_text`、`image_generated_description` の由来、各本文のhashを保持する。
- `search_keywords`、`query_rewrites`、`answerable_questions` の型付きフィールドだけを回答説明から分ける。本文中の語を検索・削除しない。可視欄やnative本文に同じ語がある場合は保持する。
- 視覚説明の旧整形全文は索引側に残す。分割境界が変わるため、全方式で旧chunk単位の検索本文がバイト一致するとは約束しない。
- 画像のrecord/example/unknown用途とは別の契約である。本契約だけで実データとしての資格や意味上の支持を認定しない。

## 保存版と再処理

新たな解析では、回答本文と索引全文を同じ構造化応答から作る。完成済み解析artifactの再利用キーには視覚本文形式v3が入るため、旧v2や版欠測の完成artifactを新形式と誤認して再利用しない。

small-to-bigの再分割では、成功した保存rawと旧整形全文が完全一致する場合だけ、作業コピーを再投影できる。現在の言語資源で照合できない本文、改変された本文、不整合の新形式を推測で補わない。元の抽出artifactは変更しない。

rawから安全に作り直せる場合は再分割・再索引、証明できない場合は再解析が必要になる。raw checkpointの再利用可否と追加の画像呼出の有無は、実際の保存状態に依存する。再解析時に必ず呼出ゼロになるとは保証しない。

本文を変更するとoffset・hash・unit IDも変わる。新しいChunk集合へ保存し、索引成功時の既存の原子的切替を使う。旧active・過去回答・引用snapshotは書き換えない。この変更で保存済み実データを一括更新・削除しない。

## 方式横断の位置と保存

`vision_text_binding` はproducerが保持する要素ID・record ID・本文hash・画像範囲を結ぶ。`vision_text_raw_projection` は全文hashと画像範囲を保持し、通常の原生文字列の行を各chunkへ複製しない。`image_ocr` は画像のOCRを同じ画像の検索補助へ結ぶ技術的な由来であり、用途のrecordへの昇格ではない。

全文を使う方式では、要素の順・区切り・本文全体が一致する組立か、parserが保存した範囲と実本文が一致する場合だけ元の位置を使う。重複する同文から最初の一致を探して画像の位置としない。新しい画像説明の書込みでは、位置が証明できる箇所を置換する。位置を証明できなければ原生prefix/suffixを残し、画像由来の新しい部分だけを既知anchorの直後、または末尾へ追加する。位置不明の原生表全体は複写しない（#4474）。

空白の圧縮・行末の正規化・文／行／表頭の分割・overlap・小chunk吸収・見出し追加と同時に範囲を移す。HTML表ではparserの行・caption・表の位置を使い、native HTMLを画像由来へ一括変更しない。親の回答本文は親本文専用hashを保存し、子のhashで親全体を認定しない。本文・検索本文が変わるときは同じ内部契約を更新し、不整合を旧fallbackで隠さない。

opaqueな原生部分は、追加された画像範囲のhashだけで文書本文の事実資格を得ない。原文範囲・画像用途の資格は既存の別契約で判断する。未記録の旧VLM由来が明示されていれば、一部の新画像が検証できても再解析を要求する。native OCRは語句やモデル名の存在だけで旧VLMと判定しない。履歴画面の保存済み本文は変更しない。
