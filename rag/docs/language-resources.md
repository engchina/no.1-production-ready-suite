# 言語資源（書き方パック）の設計

RAG が文書と質問を読むときの「言語の書き方」（数・単位・記号・助詞・参照の書き方・止め語など）を、コードから**データ**へ移す設計。

## 1. 目的と方針

- **コードには仕組み（アルゴリズム）だけを書き、言語の書き方はデータに持つ。** 漢数字の値・章や条の単位・元号・文末の記号・参照の手がかりの語・止め語などを、コードの定数や正規表現の中に書かない。
- **今までのテストで得た書き方は捨てない。** 今のコードの値を、そのまま既定の言語資源（組み込みのパック）のデータにする。既定のままなら挙動は変わらない。
- **1 つの正本にまとめる。** 同じ書き方（漢数字・単位・文末など）を各モジュールが別々に持たず、すべて言語資源から読む（今は漢数字の文字の集合だけで約 10 か所、中身もずれている）。
- **変えられる範囲を分ける。** 全体（取込・回答設定）→ ナレッジベース → 検索・回答プロファイルの順に上書きできる。
- **変えたことの影響を確かめてから使う。** 試しの文での確認、再分割が要る文書の表示、評価の実行で確かめられるようにする。

### 業界の一般的なやり方との対応

| やり方 | 例 | この設計 |
|---|---|---|
| 言語の書き方をコードから分けたデータにする | spaCy の言語データ、Lucene / Elasticsearch の analyzer の止め語・同義語のファイル、ICU / CLDR のロケールのデータ | 言語資源のパック（JSON。スキーマで検証） |
| 既定のデータを製品に同梱し、利用者が上書きする | Elasticsearch の既定の analyzer と index ごとの設定 | 組み込みのパック → 全体 → KB → プロファイルの重ね合わせ |
| 正規表現をそのまま利用者に書かせない | analyzer の設定は語の一覧と決まった型 | 語の一覧と型（`第N条`、`YYYY年度`、`一=1`）だけを受け付ける |
| 設定の変更を評価で確かめる | 検索の関連度の調整は評価セットで比べてから反映する | 試しの文の確認・再分割の対象の表示・品質評価の実行 |
| 業務の語と言語の書き方を分ける | 同義語の辞書と言語の analyzer は別 | 業務の語は既存の「用語・同義語 / ドメインキーワード / 回答ルール / 業務ガイド」、言語の書き方は言語資源 |

## 2. 何を言語資源にし、何をしないか

| 種類 | 例 | 置き場所 |
|---|---|---|
| 言語の書き方 | 漢数字の値、章・節・条・項・号の単位、元号、文末・読点・括弧、助詞、参照の手がかりの語、止め語・一般語、英語の参照の書き方 | **言語資源** |
| 文書の種類ごとの書き方 | 見出しの階層の規則、XML ツリー JSON の引用の単位、定型文（著作権・社外秘など） | **言語資源**（後で文書の種類ごとのプリセットに分ける） |
| 業務の語 | 業務の用語・同義語、ドメインキーワード、回答ルール、業務ガイド | 既存の実行時の知識（変えない） |
| LLM への指示 | プロンプト | 既存のプロンプトの管理（変えない） |
| 保存済みのデータの形 | 条の鍵「7の2」、chunk の metadata の項目名 | コードの定数（データの契約。変えると保存済みのデータを読めなくなる） |
| 検索の文の見出し | `引用:` `数:` `参照先:` など（全文検索と埋め込みに入る） | **言語資源**（変えたら再分割・再索引が要る、と画面に出す） |

## 3. 構成

### 3.1 モジュール `rag_parser_core.language`

- 共有の契約のパッケージ `rag_parser_core` の中に置く（backend・`rag_pipeline_core`・解析と分割のサービスがすでに依存している。新しいパッケージにすると 17 の `pyproject.toml` と lock と CI を足すことになるため）。`rag_engine` は段 1b で `rag_parser_core` に依存させる。依存は Python の標準ライブラリだけ。
- 中身:
  - **項目の定義**（`FIELD_SPECS`）: 節（`numbers`・`symbols`・`references`・`titles`・`english`。段ごとに足す）と項目と種類（`FieldKind`: 語の一覧・2 文字の組・型・「字=数」・「語=値」・「語=決まった値」・文字の範囲・選択）。値は持たない。
  - **組み込みのパック**（`rag_parser_core/language/packs/ja.json`。パッケージのデータ）: 今のコードの値。
  - **重ね合わせ**（`resolve(base, *overrides)`）: 上書きは項目ごとに「継承 / 置き換え」。
  - **検証と hash**（`build_pack`）: 種類ごとに形を確かめ、内容の hash を付ける。正規表現の組み立ては使う側が hash ごとに cache する（例: `reference_grammar.current_grammar`）。
  - **今の言語資源**（`current_pack()` / `bind_pack(pack)`。`contextvars`）: 取込の job・回答の要求の間だけ束ねる。束ねていなければ組み込みのパック。
- 数の読み方（漢数字・位取り）、単位の正規表現、文末の判定などの**関数**は `rag_parser_core.language` に 1 つだけ置き、各モジュールの重複を消す（段 1b）。

### 3.2 保存と重ね合わせ

| 層 | 保存先 | 画面 |
|---|---|---|
| 組み込み | `rag_parser_core/language/packs/ja.json`（読み取り専用） | 「既定に戻す」の値 |
| 全体 | backend の `language-pack.json`（組み込みとの差だけ。`RAG_LANGUAGE_PACK_FILE`） | 取込・回答設定 >「言語資源」（権限 `menu.settings_language_pack`） |
| ナレッジベース | KB の構築設定（取込の節だけ） | KB の設定（後の段階） |
| 検索・回答プロファイル | プロファイルの設定（検索・回答の節だけ） | プロファイル（後の段階） |

- 環境変数（`RAG_REFERENCE_*`）には持たない。#2157〜#2179 で足した `rag_reference_*` の設定は言語資源へ移し、消す（未リリースのため互換は持たない）。

### 3.3 実行のときの渡し方

- backend の中: 取込の job と回答の要求の初めに、その KB・プロファイルで重ね合わせた言語資源を `bind_pack` する。各モジュールは `current_pack()` から組み立て済みのものを読む。
- 解析・分割のサービス（別のプロセス）: 要求に言語資源（重ね合わせ済み）の JSON を付けて送り、サービスはその要求の間 `bind_pack` する。付いていなければ組み込みのパック。
- chunk の metadata に言語資源の hash（`language_pack_hash`）を残し、言語資源を変えたあと再分割が要る文書を数えられるようにする。

### 3.4 変更の確かめ方

- **試す**: 画面で例の文を入れると、今の言語資源と編集中の言語資源のそれぞれで、見つかる参照・数の読み・見出しの階層を並べて出す（`POST /api/settings/language-pack/preview`）。
- **影響**: 取込の節を変えたら、再分割が要る文書の数を出す（hash が違う文書）。
- **評価**: 品質評価の実行で、上書きの言語資源を指定して比べられるようにする（後の段階）。
- **履歴**: 保存ごとに版を残し、前の版に戻せる（後の段階）。

### 3.5 データから候補を出す（後の段階）

- 止め語・一般語の候補を、索引の語の出現の割合（文書頻度）から出し、管理者が選んで足す。言語資源は「決めた語」、統計は「候補」に分ける。

## 4. 移す順序

| 段 | 内容 | 主な対象 |
|---|---|---|
| 1a | `rag_parser_core.language` の土台（スキーマ・組み込みのパック・重ね合わせ・束ね・保存・API・画面）と、**参照の解析**（#2157〜#2179 の設定 51 項目）の移行 | `reference_grammar.py`・`cross_references.py` |
| 1b | **数と単位**（漢数字・単位・元号・文末）の重複（約 10 か所）を言語資源の 1 つの関数にまとめる。解析・分割のサービスへ要求で渡す。chunk に言語資源の hash を残す | `section_rules.py`・`rag_engine/chunking/headings.py`・`rag_parser_core/extraction.py`・`xml_tree_json.py`・`rag_pipeline_core/chunking.py`・`graph_expansion.py`・`pdf_segment_merge.py`・`enumeration.py`・`operation_audit.py`・`inquiry_conditions.py`・`value_grounding.py` |
| 2 | 取込の語: XML ツリー JSON の助数詞・止める字・検索の文の見出し、見出しの階層、定型文、ページの表記、装飾の画像の判定、表・図の内容のラベル（表の行のまとまりの見出し・表内画像・画像の説明の項目とまとまり・OCR の欄。書く側と回答の検査で読む側が同じ言語資源から作る） | `xml_tree_json.py`・`headings.py`・`layout.py`・`decorative_pictures.py` ほか |
| 3 | 全文検索の語: 止め語・一般語・語の端の助詞・丁寧語・英語の変化（検索だけの項目。言語資源に取込の項目だけの hash を足し、chunk にはそれを残すので、検索の語を変えても文書は古くならない） | `text_search_tokenizer.py` |
| 4 | 質問の理解の語（文書の種類・疑問・網羅・図の語）。業務に寄るものはドメインプロファイルと分ける。4a: 質問の目的・条件・経緯・対象の手がかり（`question_cues`。task_contract）。4b: 問い合わせの条件（`inquiry_cues`。文書の種類・種別の手がかり・条件とファイルの語は取込でも使う）・列挙・網羅（`enumeration_cues`）・項目の定義（`definition_cues`）。4c: 根拠の選び方（`evidence_cues`。根拠の関連度・引用の窓・手順の行・機能の見出し・画像の要否・機能の接続）。LLM への指示の文と、検索文の不採用の理由（実行記録の文）はコードに残す | `inquiry_conditions.py`・`task_contract.py`・`enumeration.py`・`definition_evidence.py` ほか |
| 5 | 回答の検査の語・実体の索引の語 | `grounded.py`・`value_grounding.py`・`entity_index.py` ほか |
| 6 | KB・プロファイルの上書き、評価での比べ、履歴、データからの候補、文書の種類ごとのプリセット | — |

各段は「既定の言語資源で今のテストがすべて通る」ことを条件に merge する。コードに書き方が残っていないことは、段ごとに検査（日本語の字を含む文字列の定数の一覧。プロンプト・画面の文言・ログを除く）で確かめる。

## 5. 守ること

- 言語資源の項目は語の一覧か決まった型だけ（正規表現を書かせない。ReDoS と壊れやすさを避ける）。型の記号（`N`・`YYYY` など）は項目の説明に書く。
- 解析の関数は 1 回の取込で何万回も呼ばれる。組み立ては内容の hash で cache し、`current_pack()` は束ねたものを返すだけにする（設定のファイルを毎回読まない）。
- 業務の内容（顧客・制度・文書の名前）を組み込みのパックに入れない（repo は public）。
