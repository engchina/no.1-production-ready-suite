# 参考回答の生成と技術再試行

通常の回答は、検索した原文が入力の上限に入れば一度生成する。上限を超えるときは原文を外さずに分割して読み（map）、最終生成の 1 回で回答へまとめる（reduce）。生成後に正確性・全小問の網羅性を別のモデルで採点して、再検索・再生成する段は設けない。

## 原文の選択と分割読取

`generation/evidence_selection.py` の `select_evidence` が、関連度の順に重複を除いた全原文について、原文の文字予算（`RAG_EVIDENCE_BUDGET_CHARS`）と、system・prompt・出力 schema・出力予約を含むモデルの入力予算（`OCI_ENTERPRISE_AI_MAX_INPUT_TOKENS`）を確認する。

- **上限内**: 全原文を関連度の順で渡し、生成を 1 回だけ呼ぶ（モデルの呼び出しは増えない）。
- **上限を超える**: 原文を除外せず、`generation/batched_evidence.py` の `prepare_batched_evidence` へ渡す。
  1. 組分け: 文書ごとにまとめ、同じ 2 つの予算（読取の指示・修復の指摘の上限を含む）に入る組へ分ける。1 文書でも入らない原文は、章節（無ければ見出し）・段落・文の順の区切りで分ける（表は行の途中で切らず、続きの組には表頭を添える）。
  2. 読取（map）: 組ごとに 1 回、質問と組の全文を読ませ、回答を支える原文の引用単位 ID と局所的な回答（回答候補）を返させる。原文と座標は ID からコードが切り出し、モデルの文字列を原文として受け取らない。回答候補の文は、内容語がすべて選んだ原文にある文だけを残す（`verified_candidate`）。番号の範囲が不正な結果・使える出力が得られなかった組は、その組の原文の全体を残して続ける。
  3. 統合（reduce）: 選ばれた範囲と回答候補を最終生成の 1 回へ渡す。まだ上限を超えるなら、選ばれた範囲を同じ手順でもう一度読む。入れば、読取が選ばなかった原文を原質問の rerank の点数の順に予算まで補う（同じ原文の抜粋は全文に置き換える）。
  4. 回答候補は根拠の後に、根拠と同じ信頼できないデータの境界で添え、読み方（読む手がかりにだけ使い、回答と引用は原文で確かめる）は生成の入力の「今回の根拠の読み方」に、回答候補があるときだけ渡す。
- **検索拡張の根拠**（参照・実体・関係情報の印を持つ根拠。`protected_sources`）: 文書を最初の組から読み（点数の低い橋渡しの根拠を最後の組へ回さず、関連度の高い根拠と同じ組で読みやすくする）、補う順の先頭にする。最終生成へ渡す並びは関連度の順のまま。補いの検索（要求別の補完・業務ガイドの手順）で合わせた根拠は `protected_sources` にしない（主の検索の根拠と同じく関連度の順で扱い、主の検索の根拠より先に残さない。#5173）。
- **引用の確認**は分割読取でも同じ: 最終生成は最終生成の入力に入れた引用単位だけを引用でき（読取の番号は引用にならない）、引用の実在と形式だけを確かめる。

上限を超えたときの呼び出しは「組の数 × 読む回数（通常 1 回）＋最終生成 1 回」になる。組の大きさは上の 2 つの予算で決まり、専用の設定は持たない（呼び出しを減らすには `RAG_EVIDENCE_BUDGET_CHARS` を上げるか検索で渡す根拠を減らす）。各組の原文の座標・状態・件数と最終入力の測定値は `generation_input_budget`（`selection`・`batch_count`・`batches`・`reduction`）に記録する。

**回答の期限（#5204）**: 各組を読む前に、回答の期限の残りが最後の生成の 1 回の見積もり（`RAG_ANSWER_GENERATION_ROUND_ESTIMATE_SECONDS`）と確定の 30 秒より少なければ、その組から先を読まない。読み終わった組の結果に、読まなかった組の入力を読取の優先の順に入る分だけ足し、上の 3 と同じく予算まで補って最終生成へ渡す（LLM は呼ばない）。最終生成の入力に入らなかった出典の数は `excluded_span_count` として回答の未反映の案内になり、止めた理由は `generation_input_budget` の `stop_reason="deadline"` と `deadline`（残りの秒・予約・読んだ組と読まなかった組の数）に残る。読まなかった組は `batch_count` に数えない。

読取の時間切れ・縮約できない入力・出力の契約に反する失敗は、成功に置き換えず、質問に関係する資料の記載だけを示す既存の扱いへ進む（`generation_failure` の `stage` が `evidence.batch_read`）。

## 回答種別と品質

生成は同じ応答で `response_kind` を宣言する。既存の `answered`、`conditional`、`insufficient_evidence` 等へ記録する。同じ応答の要点型がすべて `gap` なのに `answered` / `conditional` を宣言した場合は `insufficient_evidence`、回答と `gap` の混在を `answered` と宣言した場合は `conditional` に整合させる。元の宣言と記録した種類は診断に残す。本文の意味・引用数・質問の網羅性で種類を再判定せず、ほかの宣言は維持する。種別は正確性の認証でも、本文を隠す条件でもない。資料不足でも、参考にできる原文・説明を残す。

実行の成功、回答の種類、品質評価は区別する。適切な拒答は完了した返信として扱うが、回答できる質問への拒答は独立の評価で不合格になり得る。技術失敗は拒答の品質成功に置き換えない。宣言の無い過去の記録は従来の構造で読む。

## 技術再試行

同じモデル・同じ論理呼出の通信障害や出力形式不正に、既定で最大 1 回再試行する。内側と外側の処理は同じ回数枠を使い、回答全体の期限・取消を優先する。低品質、部分回答、拒答を再試行の条件にしない。別モデルへの切替と、画像応答が失敗した後の文字だけの再生成は行わない。以前の代替モデル指定は通常の回答生成では使用しない。

`rag/backend/.env` の全体設定:

```dotenv
RAG_LLM_MAX_RETRIES=1
```

0 は再試行なし。設定の実効値の確認（リポジトリ直下）:

```bash
cd rag/backend
.venv/bin/python -c 'from app.config import get_settings; print(get_settings().rag_llm_max_retries)'
```

関係する合成回帰（リポジトリ直下）:

```bash
cd rag/packages/rag_engine
uv run --locked --no-sync python -m pytest -q tests/test_evidence_selection.py tests/test_batched_evidence.py tests/test_response_kind.py tests/test_llm_retry_budget.py tests/test_answer_flow_single_generation.py
```

配備は開発・CI の完了とは別の操作。配備が承認されたときだけリポジトリ直下で実行する:

```bash
sudo -n ./platform/deploy/suite-update.sh
```
