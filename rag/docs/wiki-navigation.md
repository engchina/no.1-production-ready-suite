# Wiki ナビゲーション

解析済みの原文から、原文単位ごとの短い検索用の案内（語境・質問の言い換え・一緒に読む原文単位）を事前に作り、Oracle AI Database に保存する（#4941）。この文書は構築・保存と、検索での使い方を扱う。

## 向く KB と代償

- 規則・例外・手順が複数の文書に分かれている KB で効く。合成の 12 文書の評価では、通常検索だけでは別の系列の文書の規則を使う・例外の通知を読み落とす誤りがあり、網羅性が 0.37 から 0.90 に上がった（正確性はどちらも 1.0）。
- 単一の文書だけの KB では点は上がらず、時間だけ増える。
- 代償は回答までの時間（モデルの呼び出しが 2 回増え、上の評価では 1 問 21〜36 秒が 56〜93 秒）と、構築の AI の呼び出し。短くする方法は #5437 で扱う。両方の指定の既定は OFF のままにする。

## 指定

- KB 詳細の「Wiki ナビゲーション」の「Wiki を自動構築する」で KB ごとに指定する（`PUT /api/knowledge-bases/{id}/wiki`。既定 OFF）。ON にした利用者を構築の実行者として記録し、背景の構築はその利用者の現在の権限で原文を読む。権限を失ったら構築を止めて `authorization_changed` で失敗にする。
- OFF にしても保存済みの案内は消さない。同じ文書を含む別の ON の KB では再利用する。
- 画面には所属文書の状態（未構築・待機・構築中・準備済み・更新待ち・失敗）の件数を出し、失敗した構築を再試行できる（`POST …/wiki/retry`）。本文は返さない。

## 構築

- 背景の照合（`RAG_WIKI_POLL_SECONDS` ごと。ON にした直後は即時）で ON の KB の文書を集め、文書ごとに構築する。同時に構築する文書数は `RAG_WIKI_BUILD_WORKERS`。
- 原文単位は保存された chunk から作る。実際の親の行があれば親を使い、親が子の metadata にだけある分割（small-to-big）は、同じ文書・同じ chunk_set の親 ID で子をまとめ、本文は保存された子の本文から組み立てる（metadata の写しは使わない。#4964）。各子の ID と本文の hash を保持する。派生の chunk（要約・項目）は使わない。
- 生成は OCI Enterprise AI、埋め込みは OCI Generative AI。出力は対象の原文単位 ID だけを許す schema で検証する。出力が途切れたとき、JSON・schema が不正なときは対象を二分して小さい出力で取り直す（#4977）。単一の対象でも不正なら保存せずに失敗にする。原文単位は途中で切らず、入力（`RAG_WIKI_BUILD_INPUT_CHARS`）に収まらない単位は失敗にする。
- 検証済みの単位はその都度保存し（checkpoint）、中断・時間切れの後は保存済みの単位を再利用して残りから再開する。1 回の構築の時間の上限（`RAG_WIKI_BUILD_TIMEOUT_SECONDS`）に達しても、その回で案内を保存していれば中断（`interrupted`）として次の照合で自動で続ける。中断は画面の件数で待機に数え、失敗・再試行の対象にしない（#5430）。1 件も保存できなかった時間切れだけを失敗（`timeout`）として止め、再試行を待つ。モデルの一時的な失敗（429・5xx・接続・時間切れ）は、取込の AI の呼び出しと同じ共通の実行器（`make_ai_caller`、段は `wiki_build`）で再試行し、使い切ったときだけ失敗（`build_failed`）にする。失敗のログ（`wiki_build_failed`）には失敗の種類と HTTP の状態コードを残す。原文・構築の条件（指示・モデル・予算・schema の版）が同じなら、生成をやり直さない。
- 保存と公開の前に、実行者の権限・原文の保存版（有効な chunk_set の集合）・構築の条件を確かめ直す。変わっていれば保存・公開しない。

## 文書をまたぐ関連（#5492）

- 文書の案内を公開（`READY`）した後に、同じ文書の構築の続きとして作る。各単位の案内（語境・質問の言い換え・未確認の点）を検索文にし、文書が属する「Wiki を自動構築する」が ON の KB ごとに、ほかの文書の案内をベクトル（検索文の埋め込み）と全文で探して上位 `RAG_WIKI_LINK_CANDIDATES` 件を候補にする。全組み合わせでは比べない。
- 前向き（この文書の単位 → 候補）と逆向き（候補になったほかの文書の単位 → それを見つけたこの文書の単位）を、別々に OCI Enterprise AI で判定する（`app/rag/wiki_links.py`。1 回に `RAG_WIKI_LINK_BATCH_UNITS` 件の起点。原文は単位ごとに先頭の `RAG_WIKI_LINK_SOURCE_CHARS` 字）。関係は同じ文書の依存と同じ 6 種で、出力は候補に実在する単位（要求内の短い ID）だけを許す schema で検証する。途切れた・不正な出力は起点を二分して取り直す。判定した起点と候補の組の関連は、最新の判定で置き換える。
- 状態は案内と別に文書ごとに持つ（lease・判定済みの起点の checkpoint・中断の続き・失敗の理由）。関連の構築が失敗しても案内は `READY` のまま使え、再試行（`POST …/wiki/retry`）で待機へ戻る。構築の条件（指示・モデル・候補の数・所属する KB）が変われば作り直す。文書 A の構築・更新では A から出る関連と A への関連だけを作り、KB 全体は作り直さない。

## 保存

| 表 | 内容 |
|---|---|
| `RAG_WIKI_DOCUMENTS` | 文書ごとの状態（`QUEUED` / `RUNNING` / `READY` / `FAILED`）・lease・原文と構築の条件の指紋・構築に使った chunk_set・公開した指紋・失敗の理由 |
| `RAG_WIKI_PAGES` | 原文単位ごとの案内（原文の参照と各子の hash を含む JSON）・検索用の文・埋め込み |
| `RAG_WIKI_LINKS` | 文書をまたぐ関連（起点と終点の案内・関係・短い理由・両方の原文の保存版の指紋） |
| `RAG_WIKI_LINK_DOCUMENTS` | 文書ごとの関連の構築の状態・lease・判定済みの起点・構築の条件の指紋・失敗の理由 |

- lease（`RAG_WIKI_LEASE_SECONDS`）を持つ実行だけが保存・公開できる。全単位の案内と埋め込みが揃ったときだけ `READY` にする。
- 原文の版の切替で有効な chunk_set の集合が変われば「更新待ち」になり、次の照合で作り直す。文書の削除・旧版の清掃は外部キーで案内も消す。
- 関連は起点と終点の案内（原文の保存版の指紋を含む）を外部キーで持ち、文書の削除・旧版の清掃で消える。原文の保存版が変われば、読むときの指紋の照合で無効になり、次の関連の構築で古い保存版の関連を消す。案内は KB をまたいで再利用されるので、関連の有効性は読むときに KB の所属で判定する。
- 保存した原文の参照を読むときは、すべての子が実在し、文書・chunk_set・本文の hash が一致し、現在の利用者が有効な KB から見られる場合だけ原文を返す。一つでも欠けた単位は返さない。

## KB 詳細の Wiki の図（#5502）

- KB 詳細の「Wiki ナビゲーション」のカードの最下部の「Wiki の図」で、保存済みの案内を 文書 → 章節（`section_path` の階層）→ 原文単位 の図で見る。開いたときだけ読み、初めは文書だけを出し、押すと章節・単位へ段を開く（1 段 100 件まで、続きは「さらに表示」）。検索欄（単位の見出し・章節・案内の部分一致）で単位へ移れる。
- 線は同じ文書の依存（`page_json.navigation.dependencies`）と文書をまたぐ関連（`RAG_WIKI_LINKS`）で、向きは起点 → 終点の矢印（関係は終点が起点に対して持つ役割）。関係の種類は凡例と単位の案内でアイコンと文字で示す。線は表示中の単位の間だけに引き、文書をまたぐ関連は文書・章節・単位の節点に件数（他文書へ / 他文書から）で示す。
- 単位を押すと、案内（要約・想定の質問・本文に無いこと）と出る・入る関係を横に出し、原文を既存の原文の表示で開ける。案内は「AI が作った案内です。回答の根拠ではありません」と示す。
- 範囲は文書ごとの状態と同じ条件（今の利用者が読める、この KB に所属する文書）。「Wiki を自動構築する」を OFF にしても保存済みの案内は出す。案内は今の原文の保存版で公開済み（`READY`）のものだけで、構築の条件（モデル・指示）は問わない（条件が変わって作り直す前の案内も見られる）。関連は両方の案内がこの範囲にあり公開済みのものだけ。
- API は `GET /api/knowledge-bases/{id}/wiki/graph`（総覧）・`…/wiki/graph/documents/{document_id}/tree`（段）・`…/locate`（段と位置）・`…/wiki/graph/search`・`…/wiki/graph/units/{unit_id}`（案内と関係）。読み取りは `app/clients/wiki_graph_store.py` で、検索の経路（`WikiStore`）とは分ける。


- 検索・回答プロファイルの「Wiki を使用する」（`query.wiki_search_enabled`。既定 OFF）で使う。KB の「Wiki を自動構築する」とは別の指定で、使えるのは両方が ON で、案内が現在の原文の保存版・現在の構築条件で公開済み（`READY`）の文書だけ。
- 通常検索の候補を受け取らず、原質問から独立に探す（`app/rag/wiki_retrieval.py`）。回答の始めに通常検索と並行に走り、通常検索・rerank・根拠の補いの後の合わせ込み（`independent_source_union`）で結果を待つ（#5437）。合わせ込みの前に回答が終われば（確認の質問・根拠なし・失敗）止める。
  1. 目録（文書のタイトルと版の属性）と、案内のベクトル・全文検索の候補（`RAG_WIKI_CANDIDATES`）を作る。
  2. 回答のモデルが目録から読むファイルと、その中を探す検索表現を選ぶ（1 回目。`RAG_WIKI_SELECTED_DOCUMENTS` 件まで）。
  3. 選んだファイルの案内を 1 回で読み、検索表現ごとの全文検索の順位を本文を読まずに 1 回ずつ取る（#4986）。選んだファイルの全原文単位を覆う章節の候補を `RAG_WIKI_SECTION_CATALOG_LIMIT` 件まで細かくし（親に直接属する単位は子の章節と別の候補。末尾を捨てない。#5036）、各候補に原文の字数と単位数を添える。
  4. 回答のモデルが単位と章節を選ぶ（2 回目。選んだファイルの版の属性も渡す。#5044）。選んだ章節は全体の原文を読む。
  5. 選んだ単位から、同じ文書の案内の依存と、文書をまたぐ関連（出る向きと入る向きの両方）を `RAG_WIKI_LINK_DEPTH` 段（既定 2、0〜3。0 は辿らない）まで辿る（#5492）。段ごとに関係の種類の順（例外・前提・警告・続く手順・完了の条件・参照）で、まだ読んでいない単位を全段の合計で `RAG_WIKI_LINK_MAX_UNITS` 件まで足す。一度見た単位は辿り直さない。辿るのは DB だけでモデルは呼ばない。関連は、両方の案内が今の保存版・今の構築条件で公開済みで、終点の文書が今の KB にあり今の利用者が読めるものだけを使う。段ごとに足した数（依存・関連）は回答の診断の `wiki.link_hops` に残す。
- モデルへ渡す ID は要求内の短い ID（`D1`・`U1`・`S1`）で、返った ID は候補に照合して戻す。
- 版の属性は、どの形式の文書にも付く `version_status`（`current` / 新しい版に置き換えた `superseded`）と、文書の分類の有効期間（`effective_from` / `effective_to`。設定したときだけ）の 1 件に、XML の解析器が抽出に残した版の属性（`source_key`・`revision_key`・`effective_date`・`source_status`）を加えたもの。
- 原文は保存した参照を構成子・hash・所属・権限で照合し直し、すべて揃うときだけ返す。案内・要約は回答の根拠にしない。原文には目録の版の属性を写し、出典の補助情報として生成へ渡す（引用の本文・座標は変えない）。
- 通常検索の根拠とは順位を融合しない。同じ文書・保存版・chunk の原文はすでにある根拠を使い、ほかは末尾に足す（`rag_engine.generation.evidence_union`）。足した後の原文が入力の上限を超えれば、原文を外さずに分割読取する。
- 回答のモデルを呼ぶ前に、プロファイルの指定・所属・権限・原文の保存版を照合し直す。変わっていれば回答を作らない。
- 未準備・失敗・時間切れ（`RAG_WIKI_QUERY_TIMEOUT_SECONDS`。回答の期限の残りが短ければそちら）は通常検索の根拠だけで回答を続け、回答の診断の `wiki` と縮退の記録（`wiki`）に残す。
