# Wiki ナビゲーション

解析済みの原文から、原文単位ごとの短い検索用の案内（語境・質問の言い換え・一緒に読む原文単位）を事前に作り、Oracle AI Database に保存する（#4941）。この文書は構築・保存と、検索での使い方を扱う。

## 用途と評価

- 別の文書にある規則や例外を関連付け、回答に必要な原文を探す。背景の構築で生成モデルを使い、チャット時は公開済みの索引の順位と関連から原文を取得する。
- 二段階のモデル選択を使っていた旧方式の合成 12 文書の評価では、通常検索に Wiki を加えると網羅性が 0.37 から 0.90 になった（正確性はともに 1.0）。所要時間は 1 問 21〜36 秒から 56〜93 秒になった。単一文書の評価では得点の向上はなかった。現行方式の原文の回収・最終引用・所要時間の比較は #5731 で扱う。

## 指定

- KB 詳細の「Wiki ナビゲーション」の「Wiki を自動構築する」で KB ごとに指定する（`PUT /api/knowledge-bases/{id}/wiki`。既定 OFF）。ON にした利用者を構築の実行者として記録し、背景の構築はその利用者の現在の権限で原文を読む。権限を失ったら構築を止めて `authorization_changed` で失敗にする。
- OFF にしても保存済みの案内は消さない。同じ文書を含む別の ON の KB では再利用する。
- 画面には所属文書の状態（未構築・待機・構築中・準備済み・更新待ち・失敗）の件数を出し、失敗した構築を再試行できる（`POST …/wiki/retry`）。本文は返さない。
- 一件の失敗した文書のページだけを再試行するには `POST /api/knowledge-bases/{knowledge_base_id}/wiki/documents/{document_id}/retry` を使う。指定した KB の構築実行者と対象文書の現在の所属・版を再確認し、その版の保存済みページから再開する。

## 構築

既定モデル・回答モデル・構築パラメーターを変更しても、同じ原文の公開済みの案内と関連は再構築せずに検索で使う。

「文書解析」→「解析後の処理」→「7. Wiki の構築」で、原文単位の案内と文書間の関連の判定に使う指示を個別に編集・復元できる。どちらも全 KB に共通で、次にその工程を実行するときに使う。保存だけで公開済みの案内や関連を無効化・再構築しない。

- 背景の照合（`RAG_WIKI_POLL_SECONDS` ごと。ON にした直後は即時）で ON の KB の文書を集め、文書ごとに構築する。同時に構築する文書数は `RAG_WIKI_BUILD_WORKERS`。
- 原文単位は保存された chunk から作る。実際の親の行があれば親を使い、親が子の metadata にだけある分割（small-to-big）は、同じ文書・同じ chunk_set の親 ID で子をまとめ、本文は保存された子の本文から組み立てる（metadata の写しは使わない。#4964）。各子の ID と本文の hash を保持する。派生の chunk（要約・項目）は使わない。
- 生成は OCI Enterprise AI、埋め込みは OCI Generative AI。各要求には対象と同じ文書版の保存済み参照・近接候補を入れ、目録と応答 schema はその要求内の短い ID を使う。返された ID を照合して永続 ID に戻し、妥当な項目から保存する。出力が途切れた場合は対象を二分し、一部だけが不正な場合は残りの対象だけを取り直す（#4977、#5692）。
- `RAG_WIKI_BUILD_INPUT_CHARS` に加え、指示・原文・目録・schema を含む送信時の推定トークン数を登録モデルの上限と照合する。単一の原文が収まらない場合は、保存された原文の段落末、必要なら文末で分け、同じ原文 ID の案内一件にまとめる。文末や元の範囲を確認できない場合と、一文だけで上限を超える場合は失敗にする。
- 検証済みの単位はその都度保存し（checkpoint）、中断・時間切れの後は保存済みの単位を再利用して残りから再開する。時間の上限（`RAG_WIKI_BUILD_TIMEOUT_SECONDS`。既定 12 時間）は 1 文書の構築全体の上限で、実際に構築を始めた時（lease を取った時。待機に入った時ではない）から数える（#5748）。開始の時刻は状態の行（`BUILD_STARTED_AT`）に持ち、再起動などの中断（`interrupted`）からの続きでも同じ開始から数え、再試行・原文の変更で待機へ戻すと数え直す。上限の内側では 1 回で続け、超えたら失敗（`timeout`）として止め、再試行を待つ。中断は画面の件数で待機に数え、失敗・再試行の対象にしない（#5430）。lease（`RAG_WIKI_LEASE_SECONDS`）は構築の間に 1/3 ごとに延ばし、process が止まったら lease の時間の後に次の照合が続きを拾う。モデルの一時的な失敗（429・5xx・接続・時間切れ）は、取込の AI の呼び出しと同じ共通の実行器（`make_ai_caller`、段は `wiki_build`）で再試行し、使い切ったときだけ失敗（`build_failed`）にする。失敗のログ（`wiki_build_failed`）には失敗の種類と HTTP の状態コードを残す。中断時の原文・指示・schema の版が同じなら、生成をやり直さない。
- 保存と公開の前に、実行者の権限・原文の保存版（有効な chunk_set の集合）を確かめ直す。変わっていれば保存・公開しない。

## 文書をまたぐ関連（#5492）

- 文書の案内を公開（`READY`）した後に、同じ文書の構築の続きとして作る。各単位の案内（語境・質問の言い換え・未確認の点）を検索文にし、文書が属する「Wiki を自動構築する」が ON の KB ごとに、ほかの文書の案内をベクトル（検索文の埋め込み）と全文で探して上位 `RAG_WIKI_LINK_CANDIDATES` 件を候補にする。全組み合わせでは比べない。
- 前向き（この文書の単位 → 候補）と逆向き（候補になったほかの文書の単位 → それを見つけたこの文書の単位）を、別々に OCI Enterprise AI で判定する（`app/rag/wiki_links.py`。1 回に `RAG_WIKI_LINK_BATCH_UNITS` 件の起点。原文は単位ごとに先頭の `RAG_WIKI_LINK_SOURCE_CHARS` 字）。関係は同じ文書の依存と同じ 6 種で、出力は候補に実在する単位（要求内の短い ID）だけを許す schema で検証する。途切れた・不正な出力は起点を二分して取り直す。判定した起点と候補の組の関連は、最新の判定で置き換える。
- 状態は案内と別に文書ごとに持つ（lease・判定済みの起点の checkpoint・中断の続き・失敗の理由・実際の開始の時刻。時間の上限は案内と別に数える）。関連の構築が失敗しても案内は `READY` のまま使え、再試行（`POST …/wiki/retry`）で待機へ戻る。所属する有効な KB が変われば作り直す。文書 A の構築・更新では A から出る関連と A への関連だけを作り、KB 全体は作り直さない。

## 保存

| 表 | 内容 |
|---|---|
| `RAG_WIKI_DOCUMENTS` | 文書ごとの状態（`QUEUED` / `RUNNING` / `READY` / `FAILED`）・lease・原文と構築の条件の指紋・構築に使った chunk_set・公開した指紋・失敗の理由・実際の開始の時刻 |
| `RAG_WIKI_PAGES` | 原文単位ごとの案内（原文の参照と各子の hash を含む JSON）・検索用の文・埋め込み |
| `RAG_WIKI_LINKS` | 文書をまたぐ関連（起点と終点の案内・関係・短い理由・両方の原文の保存版の指紋） |
| `RAG_WIKI_LINK_DOCUMENTS` | 文書ごとの関連の構築の状態・lease・判定済みの起点・所属する KB の指紋・失敗の理由・実際の開始の時刻 |

- lease（`RAG_WIKI_LEASE_SECONDS`）を持つ実行だけが保存・公開できる。全単位の案内と埋め込みが揃ったときだけ `READY` にする。
- 原文の版の切替で有効な chunk_set の集合が変われば「更新待ち」になり、次の照合で作り直す。文書の削除・旧版の清掃は外部キーで案内も消す。
- 関連は起点と終点の案内（原文の保存版の指紋を含む）を外部キーで持ち、文書の削除・旧版の清掃で消える。原文の保存版が変われば、読むときの指紋の照合で無効になり、次の関連の構築で古い保存版の関連を消す。案内は KB をまたいで再利用されるので、関連の有効性は読むときに KB の所属で判定する。
- 保存した原文の参照を読むときは、すべての子が実在し、文書・chunk_set・本文の hash が一致し、現在の利用者が有効な KB から見られる場合だけ原文を返す。一つでも欠けた単位は返さない。

## KB 詳細の Wiki の図（#5502）

- KB 詳細の「Wiki ナビゲーション」のカードの最下部の「Wiki の図」で、保存済みの案内を 文書 → 章節（`section_path` の階層）→ 原文単位 の図で見る。開いたときだけ読み、初めは文書だけを出し、押すと章節・単位へ段を開く（文書も各段も初回は 25 件、同じ親の続きは 25 件または最大 100 件）。検索欄（単位の見出し・章節・案内の部分一致）で単位へ移れる。
- 線は同じ文書の依存（`page_json.navigation.dependencies`）と文書をまたぐ関連（`RAG_WIKI_LINKS`）で、向きは起点 → 終点の矢印（関係は終点が起点に対して持つ役割）。関係の種類は凡例と単位の案内でアイコンと文字で示す。「関係を表示」で読み込んだ線を、表示中の単位の間だけに引く。
- 単位を押すと、案内（要約・想定の質問・本文に無いこと）を横に出し、出る・入る関係は「関係を表示」で 25 件ずつ読み、原文を既存の原文の表示で開ける。案内は「AI が作った案内です。回答の根拠ではありません」と示す。
- 範囲は文書ごとの状態と同じ条件（今の利用者が読める、この KB に所属する文書）。「Wiki を自動構築する」を OFF にしても保存済みの案内は出す。案内は今の原文の保存版で公開済み（`READY`）のものだけで、構築の条件（モデル・指示）は問わない。関連は両方の案内がこの範囲にあり公開済みのものだけ。
- API は `GET /api/knowledge-bases/{id}/wiki/graph`（総覧）・`…/wiki/graph/documents/{document_id}/tree`（段）・`…/locate`（段と位置）・`…/wiki/graph/search`・`…/wiki/graph/units/{unit_id}`（案内）・`…/units/{unit_id}/relations`（関係）。読み取りは `app/clients/wiki_graph_store.py` で、検索の経路（`WikiStore`）とは分ける。


## チャットでの検索

- RAG チャットと MCP の `rag_chat` で、検索・回答プロファイルの「Wiki を使用する」（`query.wiki_search_enabled`。既定 OFF）を有効にすると使う。対象は Wiki の自動構築を有効にした KB のうち、現在の原文の版で案内を公開した文書（`READY`）。RAG 検索と `rag_search` は原文の索引を検索する。
- 通常検索の候補を受け取らず、原質問から独立に探す（`app/rag/wiki_retrieval.py`）。回答の始めに通常検索と並行に走り、通常検索・rerank・根拠の補いの後の合わせ込み（`independent_source_union`）で結果を待つ（#5437）。合わせ込みの前に回答が終われば（確認の質問・根拠なし・失敗）止める。
  1. 今の利用者とプロファイルが読める公開版に範囲を絞り、原質問で Wiki のベクトル検索と Oracle Text 検索を並行して行う。
  2. 二つの順位から交互に重複のない単位を `RAG_WIKI_CANDIDATES` 件まで採り、先頭から `RAG_WIKI_SELECTED_UNITS` 件を辿りの起点にする。ファイル・原文・章節の選択に使った生成モデルの呼び出しは、診断の `wiki.model_calls` で 0 回と確認できる。
  3. そこから、同じ文書の案内の依存と、文書をまたぐ関連（出る向き）を `RAG_WIKI_LINK_DEPTH` 段（既定 1、0〜3。0 は辿らない）まで辿る（#5492）。段ごとに関係の種類の順（例外・前提・警告・続く手順・完了の条件・参照）で、まだ読んでいない単位を全段の合計で `RAG_WIKI_LINK_MAX_UNITS` 件（既定 999、1〜999）まで足す。1 段なら直接の参照先で止まり、2 段ならその先まで読む。一度見た単位は辿り直さない。辿るのは DB だけでモデルは呼ばない。関連は、両方の案内が今の保存版で公開済みで、終点の文書が今の KB にあり今の利用者が読めるものだけを使う。段ごとに足した数（依存・関連）は回答の診断の `wiki.link_hops` に残す。
- 版の属性は、どの形式の文書にも付く `version_status`（`current` / 新しい版に置き換えた `superseded`）と、文書の分類の有効期間（`effective_from` / `effective_to`。設定したときだけ）の 1 件に、XML の解析器が抽出に残した版の属性（`source_key`・`revision_key`・`effective_date`・`source_status`）を加えたもの。
- 原文は保存した参照を構成子・hash・所属・権限で照合し直し、すべて揃うときだけ返す。案内・要約は回答の根拠にしない。原文には目録の版の属性を写し、出典の補助情報として生成へ渡す（引用の本文・座標は変えない）。
- 辿りで見た依存・関連のうち両端が回答の原文に入るものは、両端の原文に `wiki_relations`（`relation`・役割を持つ側 `role_of`（`this` / `other`）・相手の `document_name` と `section_path`）として写し、出典の補助情報として生成へ渡す（#5500）。回答の指示には、この項目が入力にあるときだけ読み方を 1 行渡し、どちらを適用するかの判断の規則は足さない（業務ガイド・利用者の設定の責務）。新しいモデルの呼び出し・DB の照会はしない。
- 通常検索の根拠とは順位を融合しない。同じ文書・保存版・chunk の原文はすでにある根拠を使い（足さない原文の `wiki_relations` はその根拠へ写す）、ほかは末尾に足す（`rag_engine.generation.evidence_union`）。足した後の原文が入力の上限を超えれば、原文を外さずに分割読取する。
- 回答のモデルを呼ぶ前に、プロファイルの指定・所属・権限・原文の保存版を照合し直す。変わっていれば回答を作らない。
- 未準備・失敗・時間切れ（`RAG_WIKI_QUERY_TIMEOUT_SECONDS`。回答の期限の残りが短ければそちら）は通常検索の根拠だけで回答を続け、回答の診断の `wiki` と縮退の記録（`wiki`）に残す。
