# Wiki ナビゲーション

通常の vector / text 検索では、質問と表現が異なる原文や、前提・警告・例外が離れた文書を十分に集められない場合がある。Wiki は解析済みの原文から短い検索用の案内と依存先を作り、別の経路で原文に到達する。回答には現在の原文を渡す。

| KB の構築 | プロファイルの検索 | 動作 |
|---|---|---|
| OFF | OFF / ON | その KB では構築・利用せず、保存済みの案内を保持 |
| ON | OFF | 背景で構築し、そのプロファイルは通常検索を使用 |
| ON | ON | 準備済み文書だけを独立に検索し、通常検索の原文と統合 |

既定は両方 OFF。KB 詳細の「Wiki ナビゲーション」で構築を指定し、検索・回答プロファイルの「Wiki 検索を使用する」で利用を指定する。反映は保存後。未構築・待機・構築中・準備済み・更新待ち・失敗の文書数を確認でき、失敗した構築は再試行できる。

## 構築と更新

Oracle AI Database の `RAG_WIKI_DOCUMENTS` に構築状態・lease・入力指紋、`RAG_WIKI_PAGES` に原文参照と検索用案内・embedding を保存する。通常の解析や分割をやり直さない。構築用の指示・モデル・予算、原文の保存版が変われば増分構築の対象になる。生成は OCI Enterprise AI、embedding は OCI Generative AI、検索は Oracle AI Vector Search / Oracle Text を使う。

親が子の metadata にだけ保存された分割も、同じ文書・保存版の親 ID に従って原文単位へ組み直す。本文は保存された構成子から組み立て、各子の ID と本文ハッシュを保持する。引用の読取ではすべての構成子の実在・保存版・本文を照合し、一つでも欠けた単位は採用しない。

取込成功・KB への文書追加で背景処理へ通知し、定期照合で再起動や通知漏れも回復する。同じ入力の準備済み案内は再利用する。切断された出力は対象単位の組を二分し、検証済みの完了単位を再利用する。原文単位が入力予算を超える場合は失敗を表示し、本文を途中で切って成功扱いにはしない。

文書の更新では現在の有効な chunk_set の集合と照合し、旧版の案内を検索対象から外す。文書削除・原文の保存版の清掃では外部キーで案内も削除する。KB から外した原文や、現在の利用者に見えなくなった原文は検索・回答に使わない。共有文書の案内は、別の有効な KB の範囲では再利用できる。OFF にした KB のキャッシュ保持は、元文書の削除後の保持を意味しない。

## 検索と合流

通常検索の候補を Wiki へ渡さず、原質問・現在の対象範囲から検索する。軽量経路は生成モデルを呼ばずに案内を検索し、依存する原文を展開する。通常の根拠補完では、予算内でファイルを選び、選んだファイルの単位・章節を選択する最大 2 回の構造化計画を行う。章節を選んだらその原文単位をまとめて読む。利用者が指定した版・時点・分類・ページ・権限の条件は拡張しない。

ファイルの目録には、解析結果に保存された文書 ID・改訂 ID・適用日の情報を添える。値がない場合は推定しない。計画に渡す ID は要求内の短いハンドルに置き換え、返却後に元の ID と対象範囲を検証する。質問と本文は置換しない。ファイルを選んだ後の読取計画では、各ファイルの先頭候補を最低一つ保持し、末端の章節を選んだ場合はその全単位を読む。依存先の展開は設定した深さまでとし、未展開の境界を診断に残す。

両経路の採用原文を最後に集合として統合する。通常検索の順番・本文を保ち、同じ原文位置の重複には経路の記録を統合する。異なる保存版や文書は同じ本文でもまとめない。Wiki の要約や質問の言い換え、構築時の未確認事項を引用根拠にしない。引用・強調表示は既存の原文 chunk の情報を使う。

Wiki が未準備・失敗・時間切れの場合は `diagnostics.wiki` と縮退の記録で区別し、通常検索の結果を返す。Wiki の原文を採用した後に設定・権限・保存版が変わった場合は、次のモデル入力の前に検出して処理を止める。

## 予算と制約

`.env.example` の `RAG_WIKI_*` に構築の並行数・入力・期限、検索候補・ファイル・原文単位・章節の選択数と期限を置く。構築は文書単位、検索時の補助計画は最大 2 回。既存の回答生成・入力予算・引用検査を共有する。独立原文を統合した入力が予算に収まれば、そのまま生成する。収まらない場合は既存の分割読取で全件を読み、選択した原文位置を最終生成へ渡す。統合後に関連度だけで未読の原文を落とさない。一般のチャットがゼロ生成モデルで検索を完了する保証はない。

大きな文書では構築入力の全原文を入れられないことを `document_complete=false` で明示する。構築済みの原文参照は正確に検証するが、モデルが意味上必要な全依存先を発見することまでは保証しない。案内のベクトル検索は現在の対象集合に対する正確な距離順であり、専用の近似索引は追加していない。大規模コーパスでは検索時間・読み取り量と選択上限の測定が必要。

`RAG_WIKI_LOOKUP_WORKERS` は案内の検索、`RAG_BATCH_READ_WORKERS` は独立した原文の分割読取の並行数を決める。分割読取は既定 1、上限 8。並行時は空いた枠から次を開始し、結果と引用の順番は元の入力順に保つ。要求の権限・期限・追跡の context も各呼出へ渡す。読取対象を減らすことで高速化する設定ではない。入力の測定では、原文の下限だけで容量超過が確定するときは巨大な全文の描画を省く。引用の snapshot に周辺本文の検査用コピーを重複保存しない。

通信・構造化出力・文字が破損した回答単位の再試行は同じ生成の予算を共有する。同一応答の完了本文が破損していて、出典の一致する完全本文の event があるときは既存のストリーム復旧を使う。それでも残った文字の破損は、同じ原文を再利用して影響を受けた回答・参考資料などの単位だけを再試行する。正常な単位は保ち、復旧できなかった単位は部分失敗として明示する。schema と引用の検査は継続し、文字の破損だけで構造化出力全体を拒否しない。

## 既存環境への切替前の確認

部分失敗の表示に `answer_labels.answer_part_generation_failed` を追加する。保存済みの言語資源にこの項目がない場合は、Wiki を無効にしていても現行の完全な保存契約に合わない。merge・配備前に[言語資源のデータ準備の門禁](language-pack-current-contract.md#配備前のデータ準備の門禁)に従って保存原値を読み取りだけで確認する。必要な修復は同文書の `language_pack_repair_cli` の dry-run で候補と取込 hash の不変を確かめ、許可を受けて新しい公開版を発行する。既存の公開版・hash・履歴は書き換えず、読み取り時の暗黙の補完は追加しない。

考え方の参照: [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval) の事前文脈化、[Microsoft の文書分割](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents) の構造単位とメタデータ、LLM Wiki の蓄積した案内から原文へ辿る考え方。別の SaaS・LLM provider・vector DB は導入しない。
